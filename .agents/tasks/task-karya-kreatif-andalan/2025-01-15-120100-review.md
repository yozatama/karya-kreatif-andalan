# Security and correctness fixes for vehicle rental platform (v2)

The commit addresses all 9 issues raised in the v1 review: JWT secret now throws on missing config, OTP response no longer leaks the code, payment webhook validates Xendit's callback token, booking endpoints check ownership, the Zustand store starts unauthenticated, middleware parses a structured JSON cookie with role, the login route stores that JSON, shared enums match the implementation, and repeat-driver analytics uses a correct >1 booking filter. A health check endpoint was also added.

**Watch for:** The webhook token validation fails closed when `XENDIT_CALLBACK_TOKEN` is unset (all webhooks rejected), but the env var is missing from `.env.example` — operators will silently lose payment callbacks (confirmed). The `addCheckpoint` endpoint still lacks an ownership check, letting any authenticated user add checkpoints to any booking (confirmed). The cookie is `httpOnly` but unsigned — the middleware trusts its JSON content (role field) without server-side verification, so a client with cookie-editing tools can escalate to admin (confirmed, pre-existing but not fully addressed by fix #6).

## High-level view

Both `auth.module.ts` and `jwt.strategy.ts` now throw synchronously at module initialization if `JWT_SECRET` is absent, meaning the app won't start in a misconfigured deployment.

The webhook validation adds header-based token checking that matches Xendit's documented `x-callback-token` mechanism. The implementation is fail-closed: if the env var is unset, every webhook request is rejected. But `XENDIT_CALLBACK_TOKEN` is not listed in `.env.example`, making silent payment failures likely in new deployments.

The booking authorization fix applies ownership checks to `GET :id` and `PATCH :id/return` but not to `POST :id/checkpoint`. The checkpoint endpoint remains open to any authenticated user, creating the same IDOR pattern that was fixed in the other two endpoints.

The frontend auth cookie now stores `{ id, email, role }` as JSON, and the middleware parses the role field for access control. The cookie is not signed — any user can craft `{"id":"2","email":"admin@karyakreatif.co.id","role":"admin"}` in their browser's cookie jar to gain admin access. The `httpOnly` flag prevents JavaScript access but not manual cookie manipulation via devtools or intercepting proxies.

The repeat-driver analytics now correctly distinguishes "has any booking" from "has more than one booking" by fetching drivers with booking counts and filtering in application code. The approach loads all matching drivers into memory, which won't scale with a large driver base.

<summary>Issues (4)</summary>

1. **Missing XENDIT_CALLBACK_TOKEN in .env.example** — Add `XENDIT_CALLBACK_TOKEN=your-xendit-callback-token` to `.env.example` so operators know to configure it. Without it, all payment webhooks are silently rejected.
2. **addCheckpoint lacks ownership check** — `POST /bookings/:id/checkpoint` accepts any authenticated user. Add the same ownership-or-admin check applied to `findById` and `requestReturn`.
3. **Unsigned auth cookie allows role escalation** — The middleware trusts the `role` field from an unsigned JSON cookie. Consider signing the cookie (e.g., with `iron-session` or a simple HMAC) so the server can verify it wasn't tampered with.
4. **Repeat-driver query loads all drivers into memory** — `findMany` + in-app filter works today but won't scale. Consider a raw SQL query with `HAVING COUNT(bookings) > 1` for large driver sets.

## Webhook token validation and deployment gap

The webhook extracts `x-callback-token` from headers and compares it against `XENDIT_CALLBACK_TOKEN` from the environment:

```typescript
async webhook(@Headers('x-callback-token') callbackToken: string, @Body() payload: any) {
  const expectedToken = this.configService.get<string>('XENDIT_CALLBACK_TOKEN');
  if (!callbackToken || callbackToken !== expectedToken) {
    throw new UnauthorizedException('Invalid callback token');
  }
  return this.paymentsService.processWebhook(payload);
}
```

When `XENDIT_CALLBACK_TOKEN` is unset, `expectedToken` is `undefined`. Any truthy `callbackToken` fails `callbackToken !== undefined`, and a missing header triggers `!callbackToken`. Both paths reject — fail-closed. However, `.env.example` only lists `XENDIT_API_KEY` and does not include `XENDIT_CALLBACK_TOKEN`, so anyone following the setup guide will have a deployment where payment webhooks never succeed.

## Checkpoint endpoint remains unguarded

The ownership check was added to `findById` and `requestReturn`:

```typescript
const booking = await this.bookingsService.findById(id);
const isAdmin = ['SUPER_ADMIN', 'OPERATIONAL_ADMIN', 'FINANCE_ADMIN'].includes(user.role?.name);
if (booking.userId !== user.id && !isAdmin) {
  throw new ForbiddenException('You do not have access to this booking');
}
```

But `addCheckpoint` passes the booking ID directly to the service without verifying ownership:

```typescript
async addCheckpoint(@Param('id') id: string, @Body() dto: CreateCheckpointDto) {
  return this.bookingsService.addCheckpoint(id, dto);
}
```

A driver could add fabricated checkpoint data (photos, odometer readings, checklists) to another driver's booking.

## Cookie integrity and admin escalation

The login route stores structured JSON:

```typescript
response.cookies.set(AUTH_COOKIE_NAME, JSON.stringify({ id: user.id, email: user.email, role: user.role }), {
  httpOnly: true,
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'lax',
  ...
});
```

The middleware parses and trusts it:

```typescript
function parseAuthCookie(cookieValue: string | undefined): { id: string; email: string; role: string } | null {
  if (!cookieValue) return null;
  try {
    const parsed = JSON.parse(cookieValue);
    if (parsed && parsed.id && parsed.role) return parsed;
    return null;
  } catch { return null; }
}
```

Since the cookie is unsigned, any user who can see the cookie format can set `role: "admin"` and access `/admin` routes. The fix moved the escalation vector from "know the admin ID" to "set role=admin in JSON" — the attack surface is the same width.
