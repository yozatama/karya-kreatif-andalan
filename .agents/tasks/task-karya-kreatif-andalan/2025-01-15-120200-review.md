# Security and correctness fixes for vehicle rental platform (v3)

This commit addresses the 4 issues raised in the v2 review: `XENDIT_CALLBACK_TOKEN` is now documented in `.env.example`, `addCheckpoint` verifies booking ownership before allowing writes, the auth cookie is HMAC-signed via a new `cookie-utils.ts` module with constant-time comparison, and the repeat-driver query uses Prisma `groupBy` with `having` to avoid loading all drivers into memory. The middleware and `auth.ts` were refactored to async to accommodate the Web Crypto HMAC verification.

**Watch for:** The register route still writes an unsigned raw user ID as the cookie value, which will fail HMAC verification in the updated middleware — newly registered users are immediately treated as unauthenticated (confirmed). The `AUTH_SECRET` env var used by `cookie-utils.ts` is not documented in the web app's `.env.example`, and the hardcoded fallback `'dev-secret-change-in-production'` will silently be used in production if the var is absent (confirmed). The `getCurrentUser` function in `auth.ts` retains an unsigned JSON fallback path that bypasses the HMAC protection when called directly (likely — middleware is protected, but any server component importing `getCurrentUser` directly would accept forged cookies).

**Verdict**: NEEDS_CHANGES — The register route incompatibility is a functional regression that will break new user signups.

## High-level view

The cookie signing implementation uses HMAC-SHA256 via Web Crypto (Edge Runtime compatible) with constant-time comparison to prevent timing attacks. The middleware correctly rejects unsigned cookies, closing the admin escalation vector from v2.

The checkpoint ownership fix mirrors the pattern already established for `findById` and `requestReturn` — same admin-role list, same `ForbiddenException`.

The `groupBy` approach for repeat-driver counting pushes the aggregation into the database, resolving the scalability concern from v2.

The register route was not updated alongside the login route. It still writes `newUser.id` (a raw string) as the cookie value. The middleware's `parseAuthCookie` calls `verifyCookie`, which checks for a dot separator and validates the HMAC — a raw ID string has no dot, so `verifyCookie` returns null, and the user is treated as unauthenticated immediately after registration.

1. **Register route writes unsigned cookie** — `apps/web/src/app/api/auth/register/route.ts` sets the cookie to `newUser.id` (raw string). The web app's `.env.example` does not list `AUTH_SECRET`. In production, if the env var is missing, the app silently uses the fallback — anyone who reads the source code can forge valid signed cookies. Add `AUTH_SECRET` to `apps/web/.env.example` and consider failing fast (like the JWT secret does) instead of falling back.
3. **getCurrentUser unsigned JSON fallback** — `auth.ts` falls back to parsing unsigned JSON if `verifyCookie` fails. The middleware is protected (it only trusts `verifyCookie`), but any server-side code that calls `getCurrentUser` directly (e.g., API routes, server components) will accept forged unsigned cookies. Remove or gate the fallback behind a migration-period flag.

## Register route cookie incompatibility

The login route was updated to sign cookies:

```typescript
// login/route.ts
const cookieData = { id: user.id, email: user.email, role: user.role };
const signedValue = await signCookie(cookieData);
response.cookies.set(AUTH_COOKIE_NAME, signedValue, { ... });
```

The register route was not updated:

```typescript
// register/route.ts
response.cookies.set(AUTH_COOKIE_NAME, newUser.id, { ... });
```

The middleware now requires signed cookies via `verifyCookie`. A raw string like `"1705123456789"` has no dot separator, so `verifyCookie` returns null at the `lastIndexOf('.')` check. The user lands on a protected route, middleware sees no auth data, and redirects to login.

## AUTH_SECRET deployment gap

The HMAC signing depends on `process.env.AUTH_SECRET`:

```typescript
const AUTH_SECRET = process.env.AUTH_SECRET || 'dev-secret-change-in-production';
```

This is the web app's secret, separate from the API's `JWT_SECRET`. The web app's `.env.example` lists `NEXTAUTH_SECRET` (a NextAuth artifact) but not `AUTH_SECRET`. A production deployment that follows the `.env.example` will have no `AUTH_SECRET` set, silently using the hardcoded fallback. This defeats the HMAC protection entirely — an attacker who reads the open-source code can compute valid signatures for any payload.

The API backend took the opposite approach for `JWT_SECRET` — it throws at startup if missing. The same pattern should apply here.

## Unsigned fallback in getCurrentUser

`auth.ts` tries three strategies in sequence: signed cookie verification, unsigned JSON parsing, and raw user ID matching. The second and third fallbacks re-introduce the exact vulnerability the HMAC signing was designed to close. The middleware is safe because it calls `verifyCookie` directly, but `getCurrentUser` is exported and available to any server-side code in the Next.js app. If a dashboard page or API route uses `getCurrentUser` for authorization decisions, the unsigned fallback allows escalation.
