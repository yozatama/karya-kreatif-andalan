# Fullstack car/motorcycle rental platform (Karya Kreatif Andalan)

A greenfield monorepo delivering a NestJS backend (11 domain modules, JWT auth, RBAC, Prisma/MySQL) and a Next.js 14 frontend (public marketing site, user dashboard, admin panel). The platform targets ride-hail drivers renting vehicles, with booking, payment (Xendit placeholder), verification, maintenance, and support workflows. Architecture is clean and consistent, with proper separation of concerns in the backend and a well-structured App Router layout on the frontend.

**Watch for:** Client-side role cookie driving admin access control in middleware is trivially spoofable (confirmed). The payment webhook endpoint has no signature verification, accepting arbitrary payloads (confirmed). JWT secrets fall back to hardcoded defaults that would silently pass in production if env vars are missing (confirmed). The frontend is entirely client-rendered with hardcoded mock data and no actual API integration (confirmed).

## High-level view

The backend follows a disciplined NestJS module-per-domain structure with global Prisma, validation pipes, and a transform interceptor wrapping all responses. Auth uses Passport JWT with refresh tokens, and an RBAC guard checks role names from the database. The Prisma schema is comprehensive with proper relations, FK indexes, and domain enums, though it lacks composite indexes for common query patterns like booking overlap checks.

The frontend middleware protects `/dashboard` and `/admin` routes, but the admin gate reads a plain `user-role` cookie that any client can set. All frontend pages are `"use client"` components hydrating from mock data in TypeScript files; there is no API client layer, no `fetch` calls, and no server components that fetch real data. This is a UI prototype, not a connected application.

The payment system has a public webhook endpoint (`@Public()` decorator) that performs no HMAC/signature validation on incoming Xendit callbacks, meaning anyone who discovers the URL can mark payments as paid. Booking logic validates vehicle availability and date ordering but does not check for overlapping reservations on the same vehicle.

The monorepo scaffold (pnpm workspaces + Turborepo) is minimal and correct. A `packages/shared` module exports Zod schemas and TypeScript types, but neither the backend DTOs nor the frontend forms import from it, making it dead code with divergent validation rules (password min 6 in backend DTO vs min 8 in shared schema).

<details>
<summary>Issues (8)</summary>

1. **Admin middleware spoofable via cookie** — The Next.js middleware reads `user-role` from a plain cookie to gate `/admin` routes. Replace with a signed/encrypted cookie or validate the JWT server-side in middleware.
2. **Payment webhook accepts unsigned payloads** — `POST /api/payments/webhook` is `@Public()` with no Xendit callback token verification. Validate `x-callback-token` header against `XENDIT_CALLBACK_TOKEN` config before processing.
3. **JWT secrets silently fall back to hardcoded defaults** — If `JWT_SECRET` or `JWT_REFRESH_SECRET` env vars are missing, the app runs with `"default-secret-change-me"`. Fail loudly at startup instead.
4. **No overlapping booking check** — `BookingsService.create` verifies vehicle availability status but does not query existing bookings for date-range overlap, allowing double-booking.
5. **Shared package unused** — `packages/shared` exports Zod schemas and types that neither the backend nor frontend imports, creating drift between validation rules.
6. **Frontend has no API integration** — All dashboard and admin pages render from hardcoded mock data. No HTTP client, no auth token forwarding, no error/loading states for network calls.
7. **`findOne` booking has no ownership check** — Any authenticated user can read any booking by ID. `returnVehicle` and `createCheckpoint` also lack role/ownership guards.
8. **Vehicle `create`/`update` uses `as any` cast** — `VehiclesService.create` and `update` cast the DTO to `any` before passing to Prisma, bypassing type safety.

## Middleware auth is client-forgeable

The Next.js middleware at `apps/web/src/middleware.ts` protects admin routes by reading a `user-role` cookie:

```typescript
if (pathname.startsWith("/admin")) {
  const role = request.cookies.get("user-role")?.value;
  if (role !== "admin") {
    return NextResponse.redirect(new URL("/dashboard", request.url));
  }
}
```

Any user can set `document.cookie = "user-role=admin"` and bypass the gate. The `auth-token` cookie existence check earlier in the middleware also performs no JWT validation — it merely checks the cookie is present. The Zustand auth store has no cookie-setting logic, so either these cookies are set elsewhere (not found in the codebase) or the middleware check never actually triggers properly.

The backend RBAC (`RolesGuard`) reads role from the JWT-validated user object, so API endpoints remain protected. But the entire admin UI is accessible to anyone who forges the cookie.

## Payment webhook lacks signature verification

```typescript
@Public()
@Post("webhook")
@HttpCode(HttpStatus.OK)
handleWebhook(@Body() payload: any) {
  return this.paymentsService.handleWebhook(payload);
}
```

The service blindly updates payment status based on `external_id` and `status` fields from the payload. The `XENDIT_CALLBACK_TOKEN` is present in configuration but never consumed. An attacker who knows or guesses an `external_id` value can POST `{ "external_id": "...", "status": "PAID" }` and mark any payment as paid.

## JWT secret fallback creates a silent production risk

```typescript
secret: process.env.JWT_SECRET || "default-secret-change-me",
```

If a deployment accidentally omits `JWT_SECRET`, the application starts successfully with a known, public secret. All tokens are then forgeable. This should throw at startup when running outside development mode.

## Booking double-booking window

`BookingsService.create` checks `vehicle.isAvailable` and `vehicle.status === "AVAILABLE"`, but the vehicle status is a global flag set to `RENTED` only when a booking transitions to ACTIVE — not when it's approved or pending. Two users can book the same vehicle for overlapping dates because there is no query checking existing bookings for date-range conflicts:

```sql
-- Missing check
SELECT * FROM bookings
WHERE vehicleId = ? AND status IN ('PENDING','APPROVED','ACTIVE')
AND startDate < ? AND endDate > ?
```

## Shared package is dead code

`packages/shared/src/schemas.ts` defines `loginSchema` (password min 8), `registerSchema`, `createBookingSchema`, etc. The backend's `RegisterDto` uses `@MinLength(6)` for password. The frontend's login page defines its own inline Zod schema also with min 6. Neither imports from `@karya-kreatif-andalan/shared`. The types in `packages/shared/src/types.ts` mirror Prisma types but are never referenced by either app.

## Frontend is a UI shell over mock data

Every page under `(dashboard)/` and `admin/` imports from `@/lib/mock-data` or `@/lib/dashboard-data`. The `useAuthStore` initializes with a hardcoded user and a `"mock-jwt-token"`. There is no API client anywhere in the frontend. The login form's `onSubmit` does `console.log("Login:", data)` and nothing else. The backend and frontend are independently well-structured but not wired together.

## `findOne` booking exposes data across users

```typescript
@Get(":id")
findOne(@Param("id") id: string) {
  return this.bookingsService.findOne(id);
}
```

The `findAll` method correctly scopes to userId for CUSTOMER role, but `findOne` performs no ownership check. A customer can read any booking by guessing UUIDs. More critically, `returnVehicle` and `createCheckpoint` have no `@Roles` guard, so any authenticated user could trigger a vehicle return or create a checkpoint on another user's booking.

## `as any` casts in VehiclesService

```typescript
async create(dto: CreateVehicleDto) {
  return this.prisma.vehicle.create({
    data: dto as any,
    include: { category: true },
  });
}
```

This defeats type safety between the DTO validation layer and Prisma's generated types. If `CreateVehicleDto` has misnamed properties or extra fields that pass `whitelist: true` (because they're decorated), Prisma won't catch them at compile time.

## Missing composite indexes

Common query patterns lack composite indexes:

- Bookings: `(vehicleId, status, startDate)` for overlap checks
- Payments: `(bookingId, status)` for payment state lookups
- Notifications: `(userId, isRead)` for unread count queries

## Test coverage gaps

The two spec files cover auth registration/login and booking create/approve/reject with proper mocking. Not tested: payment webhook handling, vehicle date-overlap scenarios, role-based access at the controller level, refresh token edge cases (expired/revoked), `returnVehicle` and `createCheckpoint` authorization, and any end-to-end integration between modules.
