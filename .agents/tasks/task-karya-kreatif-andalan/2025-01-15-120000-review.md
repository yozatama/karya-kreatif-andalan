# Greenfield vehicle rental platform: monorepo with NestJS API and Next.js 15 frontend

A pnpm/turborepo monorepo implementing a vehicle rental platform (Karya Kreatif Andalan) targeting Indonesian ride-hailing drivers renting EVs. The backend is a NestJS API with Prisma (SQLite), JWT auth, RBAC, booking state machine, payment stubs (Xendit), maintenance, notifications, support tickets, promos, and admin analytics. The frontend is a Next.js 15 app with Tailwind, Framer Motion, Radix UI, Zustand state, React Query data fetching, landing pages, user dashboard, admin panel, and two "AI" features (chatbot + damage detection). A shared package provides Zod schemas, TypeScript interfaces, and enums.

**Watch for:** The frontend is completely disconnected from the backend API — all data hooks return hardcoded mock data with `setTimeout` delays, meaning the app will never work as a connected system without a rewrite of the data layer (confirmed). The auth system on the frontend is a mock that accepts any email/password >= 8 chars and stores the user ID as the cookie value, while the backend has a real JWT system that nothing consumes (confirmed). The payment webhook endpoint has no signature verification, allowing arbitrary payment status manipulation (confirmed). The JWT secret falls back to a hardcoded string in production if the env var is missing (confirmed). The WhatsApp OTP endpoint returns the OTP in the response body (confirmed).

## High-level view

The monorepo structure is cleanly organized — pnpm workspaces, turborepo task graph, shared package with types/schemas — but the shared package is barely consumed. The backend uses `class-validator` DTOs that duplicate the Zod schemas, and the frontend hooks ignore the backend entirely in favor of in-memory mock arrays. The architectural promise of code sharing between apps is not realized.

The backend API is well-structured as a NestJS app with proper module boundaries, global validation pipes, Swagger documentation, and a clear booking state machine. However, it is effectively unreachable from the frontend. The Next.js app routes (`/api/auth/*`) implement their own mock auth that bypasses the NestJS backend completely, so the two apps are parallel implementations with no integration point.

The auth story has three incompatible layers: the NestJS backend uses JWT Bearer tokens with Passport, the Next.js API routes use cookie-based auth against a hardcoded user array, and the frontend middleware checks admin access by comparing the cookie value to a list of hardcoded IDs. These cannot work together without reconciliation.

The payment integration is stubbed but architecturally sound in structure. The critical gap is the webhook endpoint, which accepts any POST body and updates payment status without verifying the request came from Xendit. In production this allows forging payment confirmations.

The "AI" features (booking assistant and damage detection) are purely cosmetic — the chatbot is a dictionary lookup of predefined responses, and damage detection shows hardcoded results after a timeout. They demonstrate UI patterns but contain no AI integration points.

<summary>Issues (9)</summary>

1. **Frontend-backend disconnect** — All React Query hooks (`use-vehicles`, `use-bookings`, `use-payments`, etc.) return hardcoded mock data and never call the NestJS API. Replace mock `queryFn` implementations with actual `fetch` calls to the backend.
2. **Dual auth systems** — The Next.js `/api/auth/*` routes implement standalone mock auth while the NestJS backend has a full JWT system. Choose one auth strategy and wire the frontend to it.
3. **Hardcoded JWT fallback** — `jwt.strategy.ts` and `auth.module.ts` both fall back to `'super-secret-key'` when `JWT_SECRET` env var is absent. Remove the fallback and fail fast on missing config.
4. **OTP in response body** — `auth.service.ts` `whatsappOtp()` returns the OTP `'123456'` in the HTTP response. Even as a stub, this trains integrators to expect OTP in the response and risks shipping the pattern.
5. **Unsigned payment webhook** — `payments.controller.ts` `/payments/webhook` accepts arbitrary payloads with no Xendit signature verification. Add `x-callback-token` header validation.
6. **Cookie-as-identity middleware** — The Next.js middleware compares the raw cookie value to `ADMIN_IDS = ['2', 'admin@karyakreatif.co.id']`. This is not auth — it's string matching on an unsecured cookie anyone can set.
7. **Zustand store ships pre-authenticated** — `auth-store.ts` initializes with `isAuthenticated: true` and a hardcoded user, meaning the app renders as logged-in before any auth check runs.
8. **No authorization on booking read** — `GET /bookings/:id` returns any booking to any authenticated user regardless of ownership. A driver can read another driver's booking details.
9. **Shared package unused** — The `@karya/shared` Zod schemas and enums are not imported by either the API (which uses separate `class-validator` DTOs) or the frontend hooks. Remove the duplication or wire the shared schemas in.

## Frontend data layer is entirely mocked

Every React Query hook in `src/hooks/` follows the same pattern: import from a mock data file, add a `setTimeout` delay to simulate latency, and return the static array. `use-vehicles.ts` imports from `@/lib/mock-data`, `use-bookings.ts` from `@/lib/dashboard-mock-data`. None of them construct a URL, call `fetch`, or reference `NEXT_PUBLIC_API_URL`. The `useCreateBooking` mutation generates an ID with `Date.now()` and returns it — no network call.

This means the turborepo build, the NestJS server, and the Prisma database are all unreachable from the user-facing application. The frontend and backend are two independent projects that happen to share a monorepo.

```typescript
// use-vehicles.ts — representative pattern
import { vehicles } from "@/lib/mock-data";
export function useVehicles(filters?) {
  return useQuery({
    queryKey: ["vehicles", filters],
    queryFn: async () => {
      await new Promise((r) => setTimeout(r, 500)); // fake latency
      return vehicles.filter(/* in-memory filtering */);
    },
  });
}
```

## Three incompatible auth layers

The backend implements JWT via Passport:
- `JwtStrategy` extracts tokens from the `Authorization: Bearer` header
- `auth.service.ts` issues access + refresh tokens signed with `JWT_SECRET`
- `RolesGuard` checks `user.role.name` from the database

The frontend implements its own auth:
- `apps/web/src/app/api/auth/login/route.ts` validates credentials against `MOCK_USERS` (a hardcoded array of two users)
- On success, it stores the user's `id` string as the cookie value (not a token, not signed)
- Any email/password combination where password >= 8 chars authenticates as "Budi Santoso"

The middleware checks authorization:
- Compares the raw cookie string to `ADMIN_IDS = ['2', 'admin@karyakreatif.co.id']`
- This means anyone who sets `kka-auth-token=2` in their browser is admin

```typescript
// middleware.ts — admin check
const ADMIN_IDS = ['2', 'admin@karyakreatif.co.id'];
if (isAdminRoute && token && !ADMIN_IDS.includes(token)) {
  return NextResponse.redirect(new URL('/dashboard', request.url));
}
```

The cookie value is an unsigned user ID. Setting `document.cookie = 'kka-auth-token=2'` grants admin access in the frontend.

## JWT secret hardcoded fallback

Both `jwt.strategy.ts` and `auth.module.ts` contain:
```typescript
secretOrKey: configService.get<string>('JWT_SECRET') || 'super-secret-key',
```

If `JWT_SECRET` is not set in the environment (common in misconfigured deployments), all tokens are signed with a publicly known key. The application should throw on startup if `JWT_SECRET` is missing rather than falling back silently.

## OTP returned in response

```typescript
async whatsappOtp(phone: string) {
  return { message: 'OTP sent to ' + phone, otp: '123456' };
}
```

The stub returns the OTP value to the caller. Even if this is meant as a development shortcut, the response shape trains API consumers to expect the OTP in the body. A developer integrating the frontend will wire the UI to display `response.otp`, and when the stub is replaced with real WhatsApp delivery, the frontend code path breaks silently (the OTP field disappears but no error is thrown).

## Payment webhook without signature verification

```typescript
@Post('webhook')
async webhook(@Body() payload: any) {
  return this.paymentsService.processWebhook(payload);
}
```

The endpoint is publicly accessible (no auth guard), accepts any JSON body, and the service blindly trusts `payload.external_id` and `payload.status` to update payment records. Xendit sends a `x-callback-token` header that must be validated against a secret stored server-side. Without this, anyone who discovers the endpoint URL can mark any payment as `PAID` by POSTing `{ "external_id": "...", "status": "PAID" }`.

## Missing booking-level authorization

`BookingsController.findById` is protected by `JwtAuthGuard` (must be authenticated) but doesn't verify the requesting user owns the booking or is an admin:

```typescript
@Get(':id')
async findById(@Param('id') id: string) {
  return this.bookingsService.findById(id);
}
```

Any authenticated driver can read any other driver's booking details (personal information, payment history, vehicle checkpoints). The `requestReturn` endpoint has the same gap — a user could trigger return on someone else's booking.

## Admin analytics: driver retention metric is duplicated

In `admin.service.ts`, `getDriverRetention()` queries `activeDrivers` and `repeatDrivers` with identical `where` clauses:

```typescript
const activeDrivers = await this.prisma.user.count({
  where: { role: { name: 'DRIVER' }, bookings: { some: {} } },
});
const repeatDrivers = await this.prisma.user.count({
  where: { role: { name: 'DRIVER' }, bookings: { some: {} } },
});
```

Both count any driver with at least one booking. `repeatDrivers` should count drivers with more than one booking (`bookings: { some: {}, ... }`), otherwise `retentionRate` and `repeatBookingRate` always return the same number.

## Shared package type/enum drift

The shared package defines enums like `BookingStatus` with values `PENDING | APPROVED | ACTIVE | COMPLETED | CANCELLED | RETURNED`, but the backend booking service uses string literals including `REJECTED` and `RETURN_REQUESTED` which don't exist in the shared enum. The `UserRole` enum has `ADMIN | STAFF | DRIVER` while the actual system uses `SUPER_ADMIN | OPERATIONAL_ADMIN | FINANCE_ADMIN | MAINTENANCE_TEAM | DRIVER`. The shared types are already out of sync with the implementation.

## Build and deployment gaps

The API has no `nest-cli.json` or `tsconfig.build.json` visible in the diff (though `nest build` is the build script). There is no Dockerfile, no CI/CD configuration, no health check endpoint. The Prisma schema uses SQLite (`file:./dev.db`), which is not suitable for production deployment. There are no test files anywhere in the codebase despite Jest being listed in API devDependencies and a `test` script in turbo.json.

The `.env.example` references `NEXTAUTH_SECRET` and `GOOGLE_CLIENT_ID/SECRET` but the app doesn't use NextAuth — it uses custom cookie auth. These stale references will confuse deployment setup.
